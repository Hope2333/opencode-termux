## S1 机制代码定位（2.0.12 serve runtime 明文段, 1.18.32 同源）
- `LocationServiceMap.reload`: `rcMap` keys → 先逐 key invalidate（unbounded）→ 再逐 key `r.scoped(e.contextEffect(i))`（unbounded）→ **首个 failure 即 failCause** → 成功才 log "location services reloaded"
- 底层 = Effect-TS LayerMap(~effect/LayerMap): rcMap=按 key 的 scoped resource cache, contextEffect=key 的 scoped layer 构建（location={directory, workspaceID}）
- boot 在此 await 永不归 → 21 线程 futex 空转（与 T10 解剖一致）
- 日志时序校准（T10 warmup/soak 重读）: **所有冻结跑在 t+0.5~10s 即到达 "booting location services"**（warm npm cache 下安装不构成掩蔽）→ 冻结点就是 location services await 本身
- T10 warmup 尾注: 进程在 t+926s **自行退出**（非 timeout, timeout=3000s）——location await 有超时/放弃路径, 非纯死等

## S5 机制综合判读（源码 + 实验交叉）

## 终局裁决
1. **机制定位达成**: boot 死锁 = instance boot await 链（init → skill 发现 → watcher/project copy → "booting location services" → LocationServiceMap.reload → 逐 location contextEffect(Catalog+PluginBoot 层构建)）永不完成; 5c 健康时该链 ~7ms 跨过（且本地 server 37606 提供技能索引, count=24）
2. **假设 A（真实 HOME 残留 files1 陈旧态）否证**: 全盘 grep 零 files1 文本残留（含 56MB DB 二进制）; 移走全部陈旧 state 小文件后仍冻（E-A）
3. **假设 B（bun tmp 提取按路径键控）否证**: 全新 HOME/TMPDIR/XDG 零链接环境仍冻（E-B）; spinner 渲染正常说明 opentui 原生层提取/dlopen 健康
4. **「纯挂名因果」不成立**: press2ctl/press2r2（sdcard 二进制+纯沙箱, 不触及换名路径）同冻 → 10:23Z 机器级 delta 的有效成分 = 「旧健康 server 死亡 + runsv 新 serve boot 同病冻结」, TUI 与 serve 收敛到同一 await 链
5. **press3 输入轴验收仍 BLOCKED**（渲染恢复前任何二进制级修复无法在此环境验收）——下一步建议: 对 2.0.12 明文 runtime 做 serve 模式定向 strace/源码定位 location await 归宿; 或容器侧恢复 5c 态（files1 回归/重建）后复验
