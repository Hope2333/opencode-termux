  METHODOLOGY NOTE (a real trap, worth keeping): the first A4 run reported
  "0 entries checked" and still printed A4 OK. Cause: this makepkg 7.1.0 emits
  .MTREE GZIPPED, and the check did `gzip -dc` into a file, then re-read the
  file with a second `gzip -dc` — the second pass failed ("not in gzip format"),
  the process-substitution yielded nothing, and the loop body never ran. A
  vacuous pass on a zero-iteration check. Fixed by sniffing the 1f8b magic
  instead of blind-gzipping, and by adding a hard floor `N >= 6` so an empty
  iteration set can never report OK again. Any mtree check in this repo that
  lacks such a floor is suspect.

Side observation (pre-existing, NOT introduced here, NOT fixed — out of scope):
`make pacman-compressed` ended with a non-zero exit even though the package
was built correctly and every guard passed. The Makefile fallback loop globs
`packing/pacman/*-$(VER)-$(PKGREL)-*.pkg.*`, and with VER=2.0.12 PKGREL=3 that
also matches the unrelated opencode-wrapper-2.0.12-3-aarch64.pkg.tar.xz, which
pkg-abs-repack.sh then tried to repack and aborted on (tar: .INSTALL: Cannot
stat) — the wrapper package has no .INSTALL. The comment above that loop
claims it is "scoped to the EXACT pkgver just built", but the glob is not
scoped to the package NAME, only to ver+rel. Worth a pkgname qualifier
(`*-compressed-$(VER)-...` or an explicit PKG_NAME variable) before anyone
runs this target again on a shelf holding multiple families.
