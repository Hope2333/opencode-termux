安装期发现并处置（详见 §3 归位）:
  -7 的 4 个 shim 残留成「无主孤儿」——pacman 卸载 -7 时按其相对 db

  "could not get file information for usr/…" 即此）。
  这 4 个文件被 launcher 的 feature-detect 命中，会往 press5 注入:
    BUN_PTY_LIB=…/pty/librust_pty_arm64_musl_patched.so  ← musl pty

  即 press5「零外部 .so」设计要消除的两条注入路径，被旧包残骸重新接上
  （musl pty lib 强塞进 bionic 进程正是当初要规避的错库风险）。
  处置: 判 pacman -Qo 四者皆 "No package owns" → 先 tar 备份
  /mnt/sdcard_ext4/apps/a2todo16/orphan-shim-backup-20261004-174852/
  （含各文件 sha256），再删；复查 launcher 不再注入任何变量。

3. 叠影归位
════════════════════════════════════════════════════════════════════
现状: pacman.conf RootDir 已注释回落 /（前轮手修，fix19-min）。
      叠影顶层 = <原 RootDir>/data = /data/data/com.termux/files/data
      规模 1.2G / 22209 文件 / 1429 目录。

未跑 fix20 原脚本的原因（重要）:
  fix20 [12/20] 是 `pacman -Syyu` 全量系统升级，会在这台 3.18 内核机上
  重装 glibc / bash / openssh / python —— 而 ssh 通道正跑在这套包上。
  受影响集合实测含 openssh/bash/zsh/git/python/glibc/bash-completion 等
  50 包，触发全量升级风险远大于本任务归位目标。
  改为「先审计、再按内容归位」，全程零包管理事务、零网络升级。

审计（shadow-audit.sh，对 50 个受影响包逐条比对 db mtree）:
  OK=11154  RESTORABLE=2909  STALE=0  ABSENT=2
  - RESTORABLE = 正确路径缺失 + 叠影副本存在 + sha256 与 db mtree 逐条
    相符 → 纯 mv 即可还原，内容与包管理器期望完全一致。
  - STALE=0 是关键：无一例内容漂移，说明叠影副本就是包管理器装的原件。
  - ABSENT=2 是解析器对含空格文件名的假阳性
    （termux-licenses 的 "Public Domain.txt"/"VIM License.txt"），
    已单独核实两文件在正确路径均在。

归位（shadow-relocate.sh，rename 而非重装）:
  第一轮 moved=2909 skipped=0 failed=0        （正则文件）
  复检: Qk_PASS=39 Qk_FAIL=11
  第二轮 moved=980  skipped=0 failed=0        （补符号链接）
  复检: Qk_PASS=50 Qk_FAIL=0                  ✅

  第一轮漏符号链接的根因: db mtree 里 symlink 记为 type=link link=…
  且无 sha256digest，按 sha256 过滤会静默丢掉全部软链（htop/share/doc/
  copyright、git/libexec/git-core/*、libmd 全部 man/*）。审计脚本已改为
  同时处理两类条目，软链按 db 记录的目标重建（ln -sfn）。
