--- 2.2 作用域合并语义（本次最关键的实测，修正了 task-22 的旧结论）---

**本次实测证伪该结论**：v1 的 `plugin` 数组在跨 scope 时是**并集合并，不是覆盖**。

                 gstack           <- .opencode/opencode.json     scope=local
  => global 项**未被** local 覆盖，两 scope 叠加。origin 字段如实标注来源。

gstack）继续由共享 project scope 提供，合并后 10 项。**无需改写共享 ~/.opencode/**，

6. 历史会话并轨评估（只评估，未执行任何合并）
================================================================
数据：v2 DB 56MB（Jun/Sep 会话） vs v1 DB 294912B（4 条测试会话）。

**结论：不建议并轨。** 理由：
1. **代际不兼容**：v2 = 2.0.12（schema 2.0.x），v1 = 1.18.32。两代 DB schema 无
   公开兼容承诺；1.18.x 之后的表结构/字段（尤其 message part 编码与 tool 状态机）
   已多次重构。把 2.0.x 行灌进 1.18.32 极可能触发读取期异常，且 v1 无降级迁移路径。
2. **无回滚保障**：合并需写 v1 DB。备份虽在，但一旦 v1 启动时 migrate 失败，
   恢复需停进程换库，而 v1 的 session 列表/续聊链路会连带失效。
3. **收益不对称**：Jun/Sep 会话是 v2 时代的产物，其 agent 定义、模型 ID
   （deepseek-v4-flash-free 等）在 v1 侧**不存在**（provider 未移植，§5）。
   即使并轨成功，续聊时仍会因模型/agent 缺失而无法继续，得到的只是一批
   看得见点不开的历史记录。
4. **更省的替代**：真要保留历史，导出为 Markdown/JSONL 归档（`opencode export`
   或直接读 v2 DB 只读导出）即可满足查阅需求，零 schema 风险、零 v2 影响。

若用户仍决定要并轨，建议前置动作（均需另行批准）：
   a. 先在 v1 侧确认 1.18.32 的 DB schema（sqlite3 .schema）并逐表比对；
   b. 只做**只读**导出 -> 转换 -> 人工抽查 3-5 条，再谈写入；
   c. 写入前再 tar 一份 v1 DB，写入后 v1 启动失败立即换回。
