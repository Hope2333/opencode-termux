P0. 结论摘要（TL;DR）
════════════════════════════════════════════════════════════════
N2 结论：**opentui 在 glibc x64 下以「预编译独立 .so 内嵌进 bunfs」形态存在，
        但完全不需要我们交叉编译** —— 上游 npm 已有官方预编译 glibc x64 包
        `@opentui/core-linux-x64@0.4.5`（含 x86-64 glibc libopentui.so）。
        它以 `import()` 动态解析 + `new URL('./libopentui.so', import.meta.url)`
        嵌入，**不进 DT_NEEDED**。故阶段 1 不需要把 opentui 源带进跨构管线，
        也不需要为 glibc 重编 opentui。前置代理的「未取到证据 N2」到此结清。

N5 结论：**bun 1.4.0 与 1.3.14 是同款坑，且更严重**。三坑在 1.4.0 全部复现。
        但纠正配方在 1.4.0 上**照旧成立**，且实测发现一个前代理未识别的关键约束：
        `--target` token 与 `--compile-executable-path` 是**两个独立旋钮** ——
        token 只决定 JS 层烘焙（process.platform），baseline 路径只决定 ELF。
        想要「glibc ELF + linux 烘焙」必须**同时**给 musl token + glibc 路径（组合 C）。
        只给 glibc 路径仍会把 process.platform 烘成 "android"（组合 D/E）。

阶段 1 判断：**GO（有条件）**。opentui 不构成阻塞，bun 版本也不构成阻塞。
        真正的新增前置是 P8 的 `bun install --cpu=x64 --os=linux` 门控。

【实测 P13】★★★ 关键发现：token 与 baseline-path 是两个独立旋钮
  这是前代理（E1–E5）**未识别**的约束，也是本任务最重要的增量。
  5 组对照（同一 probe，同一 1.4.0，同一 glibc baseline）：

  组合  --target              --compile-executable-path   烘焙 platform/arch   实际 ELF INTERP
  A     bun-linux-x64         (无)                        android / x64        /system/bin/linker64
  B     bun-linux-x64-musl    (无)                        linux   / x64        /lib/ld-musl-x86_64.so.1
  C     bun-linux-x64-musl    <glibc>                     linux   / x64        /lib64/ld-linux-x86-64.so.2  ★
  D     bun-linux-x64         <glibc>                     android / x64        /lib64/ld-linux-x86-64.so.2
  E     (无)                  <glibc>                     android / arm64      /lib64/ld-linux-x86-64.so.2

  读法：
  · 「烘焙列」由 --target token 单独决定（A/D/E=android，B/C=linux）
  · 「INTERP 列」由 --compile-executable-path 单独决定（A/B=宿主或 musl 缓存，C/D/E=glibc）
  · ★ 唯一同时得到「linux 烘焙 + glibc ELF」的是组合 C：
      --target=bun-linux-x64-musl --compile-executable-path=<glibc baseline>
  · ★ 组合 D 是**最阴的失败模式**：ELF 看起来完全正确（glibc interp + glibc NEEDED），
    但 process.platform 烘成 "android" → 按 P11 后果，opentui 运行时 throw。
    **只 readelf 验收会漏掉它**。
  · ★ 组合 E 复现了坑3：不给 --target 时连 arch 都烘成宿主（arm64），
    产物却是 x86-64 glibc ELF —— arch 层面自相矛盾。
  → 结论：纠正配方**不是**「--target + --compile-executable-path」这么泛，
    而是**必须带 musl token**。前代理文档里的「--target=<glibc token>」表述
    在 bionic 宿主上**不可用**（那就是组合 A/D，自相矛盾）。

【实测 P16.2】本仓 store 里的副本**已被 patch 过**（所以 build-v1.sh:118 用它做 gate）

【实测 P16.3】★★ 关键：site2 使 resolver **不再读 process.platform**，
  因此会**掩盖** P13 组合 D 的烘焙错误
  纯 JS 复刻 resolveNativeLibraryPath 的真值表（host bun 跑，无编译参与）：

  场景                              烘焙 platform/arch  patch 关(应有)        patch 开(bionic 现状)
  ------------------------------------------------------------------------------------------------
  C  token=musl      (正确)         linux / x64         @opentui/core-linux-x64   同左（无差别）
  D  token=plain     (烘焙错)       android / x64       THROW(unsupported)  ←   @opentui/core-linux-x64  ← 被掩盖
  E  no --target     (烘焙错)       android / arm64     THROW(unsupported)  ←   @opentui/core-linux-arm64 ← 掩盖后更糟

【实测 P16.4】patch 能修 platform，**修不了 arch**（arch 来自烘焙，patch 不干预 process.arch）
  设产物真实机器架构恒为 x86-64（由 --compile-executable-path 决定），patch 开着时：

  场景                              patch 开启时解析到的包      .so 架构   产物架构   判定
  -------------------------------------------------------------------------------------------
  C  token=musl      (linux/x64)    @opentui/core-linux-x64     x86-64    x86-64     OK
  D  token=plain     (android/x64)  @opentui/core-linux-x64     x86-64    x86-64     OK（表面正常）
  E  no --target     (android/arm64) @opentui/core-linux-arm64  arm64      x86-64     *** 错架构 .so → dlopen 失败 ***

★ 对 P11/P13 的【自我更正】：
  本文件 P11 写「组合 D → TUI 100% 起不来」、P13 写 D 是「最阴的失败模式」——
  这两条**只在 apply-platform-patch.sh 撤掉后成立**。
  patch **开着**时 D 表面上完全正常（选中正确的 x64 glibc 包，产物出、
  readelf 全对、TUI 能起），代价是**掩盖了配方回归**：配方一旦退回
  `--target=<glibc token>` 没有任何信号，直到某天换 glibc 版本才炸。
  即 patch 在 glibc 线的作用不是「破坏」而是**「让错误静默通过」**，
  这比直接报错更危险。

【实测 P16.5】patch 两侧对「可嵌入平台包集合」无影响
  $ 对 chunk 原文与已 patch 副本分别正则提取平台包引用

                       core-linux-arm64-musl, core-linux-x64, core-linux-x64-musl,
                       core-win32-arm64, core-win32-x64]
  PATCHED  : 8 refs -> （同上，逐项相同）

    运行时烘焙值 + 平台包是否已安装（P15），不是 patch 本身。

【通则（本任务最可复用的结论）】
  **bionic 线的每个 patch 都是 glibc 线的地雷，因为它们的存在理由是
  「宿主 == 目标」，而跨构恰恰打破这个前提。**
  · `if (true)`（本条）：把「运行时探测」换成「硬编码假设」
  · TLSDESC 离线手术（shim-porting.md §2）：把「链接期放松」换成「离线改写」
  两者都编码了 bionic 宿主这一前提。
  推广：阶段 1 的 patch 清单必须**逐条显式判定撤/留**，不能整体套用 bionic 配方；
  带上最坏的结果不是报错，而是**掩盖配方错误**（if (true)）或**改错架构**（arch 不受控）。
  判据：凡「把运行时探测换成常量」的 patch，在目标≠宿主时一律撤；
      凡「离线改写产物」的 surgery，在目标 arch≠宿主 arch 时一律撤。

【N5 未取到证据 N5-d】P16.3/P16.4 的真值表是**纯 JS 复刻 + 逻辑推演**，
  未在「真实 glibc 产物 + 真实 patched chunk」上端到端跑过 —— 因为本机
  aarch64 跑不了 x86-64 产物（与 N2-a 同源限制）。
  阶段 1 可在原生 x64 runner 上补：撤 patch 后跑组合 D，断言 TUI 报
  "OpenTUI is not supported"；再装回 patch 跑同一组合，断言**反而能起**（反证掩盖）。
