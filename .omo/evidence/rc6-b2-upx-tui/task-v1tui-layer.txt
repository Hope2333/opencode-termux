# task-v1tui-layer — v1 TUI 崩因层位判决实验（UPX press 层 vs runtime 层）

日期：2026-10-02　执行：attr-v1tui　分支：rc6-b2-upx-tui/hist-ocomp（未改仓库）

## 裁决

**V1TUI_LAYER: runtime**（置信度：高）

- 未压 v1 1.18.32 runtime 的 TUI 在 oscar（kernel 3.18 / bionic 9）真 PTY 确定性崩，
  签名与压件逐字节相同 → UPX press 层对 TUI 崩溃无罪（serve 崩另案，-4 memfd 补丁仍有效）。
- 前置假说「epoll/syscall 缺失」早被 seccomp 实验证伪（task-hist-ocomp），本实验补齐判决矩阵最后格。

## 关键事实链

1. **bun 版本同源**：未压 v1 runtime 崩溃 banner 实证 `Bun v1.4.0 (34cbb9a40) Android arm64` ——
   与 v2 2.0.18 内嵌 bun 同 hash。bun.report 页面确认 "Embedded Bun version: 1.4.0"。
   **此前「v1 runtime = bun 1.4.2」记载（task-v1c-triage / 配方卡）对本件不成立**；
   且压件 v4 与未压件崩链逐字节相同，反推 -4 压件同嵌 bun 1.4.0（1.4.2 记载疑为该代归因讹误）。
   → 「版本差（1.4.2 vs 1.4.0）」假说出局。
2. **pty 资产切面出局**：BUN_PTY_LIB 注入 v2 已验证的 musl patched lib，崩链不变 → v1 崩点不在 pty 资产。
3. **fs 变量出局**：同签名跨 SD ext4 与 /data/local/tmp（#1-5）。
4. **press 变量出局**：未压与压件同签名（#1-2 vs #4-5）。
5. **remap 栈**（bun.report 页面程序化抓取，`bunpage.html` 逻辑已存本地 scratch）：顶帧 YarrJIT/ARM64Assembler/
   `crtstuff.c:0 bun_internal_modules_data` —— 文档已定谳此类 JSC 归因不可靠（glibc ucontext 布局读
   glibc+bionic 混合进程，pc/fp 错位），仅作崩线程身份参考。
6. **对位文档**：docs/tui-reachability.md 判据 1 —— Android 9 bionic 的 libopentui TLSDESC resolver
   槽=NULL（linker.cpp 不预填），首次 TLS 访问（zig std signal_stack，Thread.maybeAttachSignalStack 路径）
   `blr x1`→pc=0 → SIGSEGV SEGV_MAPERR@0x0。v2 经 `tools/transplant/tlsdesc-shim/`（模块内 ctor 扫
   .rela.dyn R_AARCH64_TLSDESC 回填 emutls 语义槽，bionic 10+ no-op）graft 后 oscar 4/4 渲染零崩。
   v1 1.18.32 native 线构建于 shim 落地之前（deb 2026-09-27），其内嵌 bionic opentui **无 shim**
   （shim 符号已 strip，无法 strings 指纹，以构建时序 + 症状全等推断）。

## 下一层建议（runtime 层细分）

1. **首选**：给 v1 1.18.32 native 线重打 TLSDESC shim（transplant.py graft 路线与 v2 同型，
   `tools/transplant/tlsdesc-shim/` 现成），oscar 复测 TUI。若活 → v1 判定表补判据 1 修补，
   1.18.32-5 重建链直接采用。
2. 次选归因加固（若 shim 重打后仍崩）：ckt-shim.c（sigaction-hijack）取真 pc 落点，
   判 opentui vs opencode JS 1.18.32 自身 TUI 代码。
3. 遗留小账：配方卡/ops 文档的「1.18.32 内嵌 bun 1.4.2」表述建议按本实验 banner 证据修正。
